# 通用仿生水处理设计知识库

本项目不是生物案例百科，而是面向大语言模型、设计智能体和工程模型的**可组合仿生设计知识层**。最终目标是支撑一整个仿生反应器或水处理装备的设计：从需求定义开始，检索生物机制，生成材料和微生物候选，把它们组合成组件、反应器和系统，并为运行优化与调控提供有边界、可验证的设计变量。

> 当前状态：架构 v2 已落地，包含一条标为 `unverified` 的 A²/O 端到端示范切片。现阶段重点是验证知识契约和查询链路，而不是追求条目数量。

## 这个库最终用来做什么

库面向四个相互连接的消费者契约：

1. **基于大语言模型的仿生材料设计**：从生物表面、结构、化学与形成过程提取材料功能，返回候选组成、结构、制备变量、适用边界和验证方法。
2. **仿生微生物设计**：从代谢、群落分工、空间组织、反馈和韧性机制出发，返回功能菌群、空间配置、运行窗口和稳定性约束。
3. **仿生反应器与装备设计**：把材料、微生物、组件、反应器和系统模块组合成整机候选，显式记录模块接口、兼容性、工程约束和验证状态。
4. **运行优化与调控**：围绕已经定义的装备，连接传感状态、可操作杠杆、控制参数、不可违反的约束和验证过的策略。

前三者不是独立的资料库。材料和微生物是可被反应器装配的设计模块，运行控制是装备的一部分。一个完整设计输出至少应回答：

- 要解决什么问题，优化什么指标？
- 借鉴哪个生物原型的哪种机制？
- 机制如何被转译成材料、微生物、组件、反应器或控制模块？
- 模块之间通过什么接口组合，是否兼容？
- 哪些参数可进入 DFT、MD、CFD、ASM、优化器或控制器？
- 哪些工程约束会排除这个候选？
- 哪些结论已有文献、仿真、实验或实测支持，哪些仍是假设？

## 总体设计链

```text
设计需求 / 工艺情境 / 性能目标
                  ↓
           生物原型 → 生物机制
                  ↓
              Design Mapping
                  ↓
  材料模块 ─ 微生物模块 ─ 组件模块 ─ 反应器模块 ─ 系统模块
                                      ↓
                                  控制模块
                  ↓
        Assembly Pattern（整机装配模式）
                  ↓
        文献 / 仿真 / 实验 / 实测验证
```

核心知识单元是 `DesignMapping`，不是一篇原型文章。它表达：**一种生物机制在特定问题和工况下，如何被转译为工程模块、可操作杠杆和参数，并受到哪些约束和证据支持。**

`AssemblyPattern` 用来组成完整装备。它引用已有模块，而不复制模块内容，因此同一个材料或微生物模块可以进入不同反应器方案。

## 为什么不是一张巨型矩阵

库同时包含问题、工艺、污染物、目标、生物原型、机制、尺度、模块、参数、约束和证据等维度。把它们人工展开成一张高维表，会产生大量空单元和重复事实。

因此本项目采用：

- **底层：实体 + 显式关系**，同一事实只维护一次；
- **上层：按查询生成矩阵视图**，例如“问题 × 模块层”“机制 × 工程杠杆”“工艺 × 设计候选”“参数 × 证据状态”；
- **LLM：负责语义解析、候选组合和解释**；
- **结构化查询：负责硬约束、数值边界、证据状态和一致性**；
- **仿真/实验：负责证明或证伪**，库本身不冒充优化器或仿真引擎。

## 当前实质内容

当前知识层包含一条 A²/O 纵切片：

- 情境：既有 A²/O 在低 C/N 与进水波动下运行；
- 原型：微生物席；
- 机制：氧化还原分层、反应锋面迁移；
- 微生物模块：氧化还原分层功能群落；
- 反应器模块：可独立曝气的串联分区反应器；
- 控制模块：受约束的自适应氧化还原锋面控制；
- 装配模式：自适应分区仿生 A²/O 反应器；
- 验证：计划使用动态 ASM2d 对照、参数扫描和消融实验；
- 成熟度：全部保持 `unverified`，直到文献核实和仿真通过。

这是一条用于验证架构和查询链路的样本，不是可直接交付工程的成熟方案。

## 快速开始

本项目的知识工具只使用 Python 标准库。

```powershell
# 1. 校验实体、关系、必填字段和证据纪律
python scripts/knowledge.py validate

# 2. 查询控制层设计模块
python scripts/knowledge.py query --type DesignModule --where layer=control

# 3. 查询 A²/O + 低 C/N 的反应器设计候选
python scripts/knowledge.py design --consumer reactor_design --process A2O --problem low_cn

# 4. 查看整机候选及直接关系
python scripts/knowledge.py show --id assembly_adaptive_a2o_reactor

# 5. 生成矩阵和覆盖率视图
python scripts/knowledge.py generate

# 6. 运行回归测试
python -m unittest discover -s tests -v
```

## LLM / ML 应如何使用

### 大语言模型

LLM 应先把用户问题解析为结构化条件，例如：

```json
{
  "consumer": "reactor_design",
  "process": "A2O",
  "problems": ["low_cn", "tn_instability"],
  "constraints": ["no_major_civil_rebuild"],
  "targets": ["tn_stability", "aeration_energy"]
}
```

然后调用结构化查询获得候选，再解释机制、模块、参数、约束和证据。LLM 不得凭语言相似度覆盖硬约束，也不得把 `unverified` 改写为成熟结论。

### 机器学习

在积累足够的 `ValidationRun` 或实验数据之前，不应训练参数预测器。未来 ML 的合理位置是：

- 对候选 `DesignMapping` 进行排序；
- 基于仿真/实验数据预测参数与性能；
- 构建 DFT、CFD、ASM 或控制系统的代理模型；
- 发现兼容模块组合。

模型输出仍是候选或估计，必须回写证据来源、适用域和验证状态后才能进入知识层。

## 建库工作流

每条新内容采用纵切片方式进入：

1. 固化一个消费者、一个真实问题、输入约束和预期输出。
2. 创建或复用生物原型与机制；不得因同义词重复建实体。
3. 创建原子化 `DesignMapping`，连接情境、目标、模块、杠杆、参数和约束。
4. 如形成装备候选，创建 `AssemblyPattern` 并说明模块接口与兼容性。
5. 为每项关键主张添加 `EvidenceClaim` 和可定位的 `EvidenceSource`。
6. 添加可证伪的验证计划；通过前保持 `unverified`。
7. 运行校验、测试和矩阵生成后再提交。
