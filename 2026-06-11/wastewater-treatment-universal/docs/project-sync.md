## 1. 项目背景

### 1.1 起点

现有项目"仿生吸附材料知识库"（GitHub: `YaoPan-NJU/Biomimetic-design-library`，`feature/extraction-results` 分支）已完成 33 个吸附相关生物原型的知识库建设，具备完整的 YAML 元数据 + Markdown 正文结构。

### 1.2 扩展动机

吸附材料只是水处理仿生设计的一个子方向。实际工程中，仿生设计的适用范围远不止材料合成，还涉及：

- **微生物设计**：群落结构、功能菌群协同、代谢路径优化
- **反应器设计**：流场布局、内构件配置、池型优化
- **元件设计**：填料几何、曝气头、膜组件
- **系统设计**：多级串联、循环回路、全流程优化
- **改造优化**：已有污水厂的提标改造、工艺优化、环节调优
- **运行调控**：基于多维传感的实时运行控制参考

因此，需要建设一个面向整个水处理过程的通用仿生设计参考库。

## 2. 关键讨论与决策

以下是讨论过程中逐一确认的核心决策：

### 2.1 核心组织单元

**决策：保持"生物原型"作为核心组织单元。**

理由：不同的水处理过程（传质、生化反应、固液分离等）都可以分别到库中匹配仿生灵感，以生物原型为中心最符合使用习惯。

### 2.2 扩展维度

**决策：同一原型多尺度扩展，不新增"工程类原型"分类。**

讨论中考虑过两种扩展方式：
- **A. 同一原型多尺度扩展**：每个原型在材料→组件→反应器→系统四个尺度上各自描述设计启示 ✅
- **B. 新增工程类原型**：单独创建"曝气池仿生"、"膜组件仿生"等工程导向原型

最终选择 A。理由：一个生物原型可能同时在多个尺度提供启示（如贻贝足丝既启发材料涂层，也启发组件锚固结构），按原型组织更自然，不需要人为拆分。

### 2.3 用户入口

**决策：五种入口并存，且特别强调已有系统的提标改造场景。**

| 入口 | 典型问题 |
|------|----------|
| 污染物 | "去除 NH₄⁺-N 有什么仿生方案？" |
| 工艺 | "我在做 MBR，有什么仿生优化思路？" |
| 设计问题 | "曝气效率低，怎么仿生改进？" |
| 改造场景 | "现有 A²/O 池想优化流场" |
| 运行调控 | "DO 偏低，怎么调曝气？" |

运行调控入口是后期补充的——在实际运行中，多维传感器实时感知全流程情况，希望调控操作时能参考仿生库获得灵感和参数参考。

### 2.4 项目关系

**决策：独立开发，完全隔离。**

新项目在 GitHub 上以**孤立分支（orphan branch）** `wastewater-treatment-universal` 开发，与旧吸附库无任何共享文件和 git 历史。后续开发完成后，吸附库数据可作为 `domains/adsorption/` 子集迁入。

### 2.5 原型方向与聚焦

**决策：12 个新方向 + 现有吸附 = 13 个领域，以生化处理段为核心（80%+）。**

讨论过程：
- 原型方向需要从**现有污水处理工艺**来分析，而非凭空设定
- 以生化处理段为核心聚焦（占库内容的 80% 以上），这是污水处理的核心环节
- 领域方向包括：流体力学、生化反应、分离/过滤、微生物群落、生物膜、代谢路径、传质与流场、固液分离、抗冲击与自恢复、**资源化**、能源/驱动、系统/群落
- **资源化方向**（碳源回收、磷回收、能源回收、再生水）是讨论中专门补充的，对应当前污水处理行业"资源工厂"的发展趋势
- 吸附领域作为第 13 个领域，后续从现有项目迁入

工艺分类的讨论共识：
- **不关注一级处理**（初沉等），聚焦二级处理
- 二级处理覆盖：活性污泥法（A²/O、SBR、氧化沟、MBR 等）、生物膜法（BAF、MBBR 等）、厌氧处理（UASB、IC 等）、组合工艺
- 辅以深度处理、污泥处理和资源化

### 2.6 工程仿真工具关联

**决策：灵感 + 参数边界，不包含仿真模型本身。**

讨论背景：团队日常使用 CFD（Fluent/OpenFOAM）、多物理场仿真（COMSOL）、活性污泥模型（ASM1/2/3）、过程仿真（GPS-X/BioWin）等工具辅助设计。讨论中明确指出当前库只有原型和原理，缺少基于工具的考量。

库的定位共识：
- 提供仿生设计灵感
- 给出可量化的关键设计参数及取值范围（每个尺度的设计参数表格）
- 标注关联的工程仿真工具（如某参数适合用 CFD 验证）
- **不包含**仿真模型文件或脚本
- 目标是让使用者拿到库中的参数后，可以直接输入到自己的仿真工具中验证

### 2.7 运行调控场景

**决策：加入运行调控路由（operation-router.json），面向已有污水厂的实时运行控制。**

这是讨论中后期补充的重要场景，也是实际使用频率最高的场景之一。讨论中描述的工作流：

```
多维传感器实时感知全流程 → 数据采集 → ASM/CFD/ML 建模分析
    → 识别需要调控的操作点 → 查询仿生库获取调控策略和参考参数
    → 操作人员决策 / 自动控制系统执行
```

关键共识：
- 库**不参与**毫秒级实时控制回路，而是作为**决策支持层**
- 调控类型分 4 类：曝气调控、流道调控、加药调控、污泥调控
- 每类调控由传感信号触发（如 DO 偏低、SVI 偏高），映射到仿生策略和参考参数
- 这个场景对已有污水厂的日常运营价值最大

### 2.8 架构选型

**决策：领域路由架构（方案 B）。**

讨论中由 plan-agent 评估了三种方案：

| 方案 | 描述 | 评估 |
|------|------|------|
| A. 保守扩展 | 在现有单文件结构上加字段 | 简单但单文件会膨胀 |
| **B. 领域路由** | 生物原型池 + 领域路由层 | **平衡成本与扩展性** ✅ |
| C. 尺度感知图 | 全图数据库 + JSON-LD | 强大但过度工程化 |

选择方案 B 的理由：
- 12+ 领域天然需要隔离建设，避免单文件膨胀
- LLM 友好（Markdown + JSON 双层结构）
- 现有吸附库可零改造成为第 13 个领域
- 支持 5 种入口的灵活路由
- 后期可渐进引入图架构元素（如原型超 150 个时引入 JSON-LD）

否决方案 C 的理由：当前阶段原型数量可控（预计 80-150 个），全图数据库的建设成本和维护成本过高，JSON 索引已能满足查询需求。

### 3.3 核心设计：多尺度原型模板

每个原型描述四个尺度的设计启示（**必填**）：

| 尺度 | 尺寸范围 | 水处理对应 | 示例启示 |
|------|----------|-----------|----------|
| 材料 | nm-mm | 吸附剂、膜材料、涂层 | 表面化学、微观结构 |
| 组件 | mm-m | 填料、曝气头、膜组件 | 几何构型、孔隙分布 |
| 反应器 | m 级 | 反应池、沉淀池 | 流场布局、内构件 |
| 系统 | m-km 级 | 污水厂全流程 | 多级串联、循环回路 |

每个尺度包含**关键设计参数表格**（参数名、取值范围、关联工程工具、说明），可直接用于仿真。

### 3.4 两阶段路由机制

```
用户输入（5种入口之一）
    ↓
第一阶段：入口路由 → 识别涉及的 1-3 个领域
    ↓
第二阶段：领域 mapping.json → 条件预筛 + weight 排序 → top N 原型
    ↓
跨域发现：查询 cross-domain-links.json → 发现关联原型
    ↓
输出：候选原型 + 多尺度设计启示 + 跨域协同建议
    ↓
LLM 读取原型详情 → 组合推理
```

### 3.5 运行调控路由

`operation-router.json` 面向实时运行场景，4 类调控：

| 调控类型 | 触发信号示例 | 调节目标 |
|----------|-------------|----------|
| 曝气调控 | DO偏低、OUR异常 | 曝气量/模式/布局 |
| 流道调控 | RTD短路、流速不均 | 进水方式/导流板/回流比 |
| 加药调控 | TN偏高、碳氮比低 | 碳源投加量/点/频率 |
| 污泥调控 | SVI偏高、MLSS异常 | 排泥量/回流比/DO |

每类包含：触发信号（传感器数据+条件）→ 调节目标 → 仿生调控策略（待填充）。
