## DD-001：核心组织单元 — 生物原型 vs 水处理过程

**日期**：2026-06-09
**状态**：已确认

### 问题

库的核心组织单元应该是什么？
- **A. 生物原型**（如贻贝足丝、红树林根系、生物膜等）
- **B. 水处理过程**（如曝气、沉淀、过滤等）

### 决策

**选择 A — 生物原型。**

### 理由

不同的水处理过程（传质、生化反应、固液分离等）都可以分别到库中匹配仿生灵感。以生物原型为中心最符合使用习惯——用户想知道"自然界有没有解决我这个问题的生物方案"，而不是"曝气这个过程有哪些生物"。

### 被否决方案

方案 B 会导致同一生物原型被拆分到多个过程目录下，信息碎片化，且不利于跨领域发现。

## DD-002：扩展维度 — 多尺度扩展 vs 新增工程类原型

**日期**：2026-06-09
**状态**：已确认

### 问题

如何从"吸附材料"扩展到"整个水处理"？
- **A. 同一原型多尺度扩展**：每个原型在材料→组件→反应器→系统四个尺度上描述设计启示
- **B. 新增工程类原型**：单独创建"曝气池仿生"、"膜组件仿生"等工程导向原型

### 决策

**选择 A — 同一原型多尺度扩展。**

### 理由

一个生物原型可能同时在多个尺度提供启示。例如：
- 贻贝足丝：材料尺度（DOPA 粘附化学）+ 组件尺度（锚固结构设计）
- 红树林根系：组件尺度（过滤结构）+ 反应器尺度（根系流场布局）+ 系统尺度（多级净化）

按原型组织更自然，不需要人为拆分。多尺度设计启示设为必填字段，迫使建库者系统思考每个尺度的可能性。

### 被否决方案

方案 B 会导致大量重复——同一个贻贝原型需要分别写"贻贝-材料"和"贻贝-组件"两条记录，维护成本高且容易不一致。

## DD-003：项目关系 — 独立分支 vs 同分支扩展

**日期**：2026-06-09
**状态**：已确认

### 问题

新项目与现有吸附材料库是什么关系？
- **A. 同分支扩展**：在 `feature/extraction-results` 分支上直接添加新目录
- **B. 独立分支开发**：新建 `wastewater-treatment-universal` 分支，后续迁入旧数据

### 决策

**选择 B — 孤立分支（orphan branch）独立开发。**

### 理由

- 两个项目的定位和目标不同：吸附库聚焦材料合成，新库面向全水处理过程
- 独立开发避免相互干扰，不需要担心破坏现有吸附库的数据完整性
- 后续开发完成后，33 个吸附原型补充多尺度描述后可作为 `domains/adsorption/` 迁入

### 实施方式

使用 `git checkout --orphan` 创建孤立分支，完全清除旧项目文件后重新搭建。Force push 到远程覆盖旧分支。两个分支无任何共享文件和 git 历史。

## DD-004：架构选型 — 三种方案

**日期**：2026-06-09
**状态**：已确认

### 问题

库的整体架构如何设计？

### 评估

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A. 保守扩展 | 在现有单文件结构上加字段和目录 | 零迁移成本，简单直接 | 原型数量增长后单文件膨胀，跨领域查询困难 |
| **B. 领域路由** | 共享原型池 + 领域路由层 | 领域隔离建设，LLM 友好，扩展性好 | 初始搭建成本稍高 |
| C. 尺度感知图 | 全图数据库 + JSON-LD | 支持复杂关系查询，理论上最强大 | 过度工程化，建设维护成本高，当前阶段不需要 |

### 决策

**选择 B — 领域路由架构。**

### 理由

1. 12+ 领域天然需要隔离建设（流体力学、生化反应、生物膜等领域各自独立发展）
2. LLM 友好：Markdown 主体 + JSON 索引的双层结构，大模型直接读取
3. 现有吸附库可零改造成为第 13 个领域
4. 支持 5 种入口的灵活路由
5. 后期可渐进引入图架构元素（如原型超 150 个时引入 JSON-LD）

### 否决 C 的具体理由

当前阶段原型数量预计 80-150 个，JSON 索引 + 路由文件已能高效满足查询需求。全图数据库的搭建和维护成本远超收益。如果未来原型数量显著增长或需要复杂的关系推理，可以渐进演化。

## DD-005：聚焦范围 — 生化处理段 80%+

**日期**：2026-06-09
**状态**：已确认

### 问题

库应覆盖水处理全过程还是有所聚焦？

### 决策

**以生化处理段（二级处理）为核心，占库内容的 80% 以上。**

### 理由

- 生化处理段是污水处理的核心环节，仿生设计的潜力最大
- 不关注一级处理（初沉等物理过程），这些过程仿生空间有限
- 深度处理、污泥处理、资源化作为辅助方向覆盖

### 工艺覆盖

- **核心**：活性污泥法（A²/O、SBR、氧化沟、MBR 等）、生物膜法（BAF、MBBR 等）、厌氧处理（UASB、IC 等）、组合工艺
- **辅助**：深度处理（混凝、高级氧化等）、污泥处理（厌氧/好氧消化）、资源化（碳源回收、磷回收、沼气等）

## DD-006：工程仿真工具关联方式

**日期**：2026-06-09
**状态**：已确认

### 问题

库与工程仿真工具（CFD、ASM、COMSOL 等）是什么关系？

### 讨论

团队日常使用 CFD（Fluent/OpenFOAM）、多物理场仿真（COMSOL）、活性污泥模型（ASM1/2/3）、过程仿真（GPS-X/BioWin）等工具辅助设计。讨论中指出当前库只有原型和原理，缺少基于工具的考量——使用者需要知道仿生灵感对应的可量化参数，以便输入仿真工具验证。

### 决策

**灵感 + 参数边界，不包含仿真模型本身。**

库的职责：
1. 提供仿生设计灵感
2. 在每个尺度的设计启示中给出**关键设计参数表格**（参数名、取值范围、关联工具、说明）
3. 标注关联的工程仿真工具（如"此参数适合用 CFD 验证"）

库不包含：
- 仿真模型文件
- 仿真脚本
- 仿真结果数据

### 设计参数表格格式

| 参数 | 取值范围 | 关联工具 | 说明 |
|------|----------|----------|------|
| 例：孔隙率 | 0.3-0.7 | COMSOL | 影响传质效率 |
| 例：HRT | 4-8 h | GPS-X | 影响处理效果 |

## DD-007：运行调控场景纳入

**日期**：2026-06-09
**状态**：已确认

### 问题

是否需要支持污水处理厂的实时运行调控场景？

### 讨论

这是讨论中后期补充的场景，也是实际使用频率最高的场景之一。实际运行中，多维传感器实时采集 DO、OUR、SVI、TN 等信号，通过 ASM/CFD/ML 建模分析后识别需要调控的操作点。希望调控操作时能参考仿生库获得灵感和参数参考。

### 决策

**加入运行调控路由（operation-router.json）。**

### 关键设计

- 库**不参与**毫秒级实时控制回路，而是作为**决策支持层**
- 调控类型分 4 类：曝气调控、流道调控、加药调控、污泥调控
- 每类由传感信号（传感器数据 + 条件）触发，映射到仿生调控策略和参考参数
- 面向已有污水厂的日常运营，使用频率高于新建项目设计

### 工作流

```
多维传感器 → 数据采集 → ASM/CFD/ML 建模分析
    → 识别需要调控的操作点
    → 查询 operation-router.json（按调控类型匹配）
    → 获取仿生调控策略 + 参考参数
    → 操作人员决策 / 自动控制系统执行
```

## DD-008：多尺度设计启示为必填

**日期**：2026-06-09
**状态**：已确认；**2026-06-10 修订（见 DD-014）**

### 问题

多尺度设计启示（材料→组件→反应器→系统）是否全部必填？

### 决策

**四个尺度均为必填字段。**

> **修订（2026-06-10）**：松绑为"**相关尺度必填、其余显式标注 N/A**"。原"强制四尺度全填"会迫使低证据尺度产出占位或被包装的猜测（chimera 风险）。"系统思考每个尺度"保留为核对清单，但不再强制填字。详见 DD-014。

## DD-009：LLM 友好的数据格式

**日期**：2026-06-09
**状态**：已确认

### 问题

库的数据存储格式如何设计？

### 决策

**Markdown 主体 + JSON 索引的双层结构。**

### 理由

- Markdown 是大模型直接读取的最友好格式，不需要额外解析
- JSON 索引用于快速查找和条件筛选，不需要逐个读取 Markdown 文件
- 路由文件（entrypoints/）也是 JSON，支持两阶段路由机制
- 避免使用数据库（SQLite、PostgreSQL 等），保持 Git 友好的纯文本存储

### 文件职责分工

| 文件类型 | 格式 | 职责 |
|----------|------|------|
| 原型条目 | Markdown + YAML 元数据 | 详细描述，LLM 直接读取 |
| 索引文件 | JSON | 快速查找、条件预筛 |
| 路由文件 | JSON | 入口路由、领域映射 |
| 分类体系 | Markdown | 标签定义、层次结构 |

## DD-010：资源化方向的纳入

**日期**：2026-06-09
**状态**：已确认

### 问题

是否需要包含资源化相关的仿生设计？

### 讨论

讨论中专门提出资源化方向，对应当前污水处理行业"资源工厂"的发展趋势。碳源回收（VFAs）、磷回收（鸟粪石结晶）、能源回收（沼气）、再生水回用等方向，都有仿生设计的潜力。

### 决策

**纳入资源化方向，作为独立领域 `resource-recovery`。**

### 覆盖范围

- 碳源回收（VFAs）：仿生发酵、代谢路径优化
- 磷回收（鸟粪石结晶）：仿生结晶、生物矿化
- 能源回收（沼气）：厌氧消化优化、微生物群落调控
- 再生水回用：仿生膜、多级净化

## DD-011：提标改造场景的优先性

**日期**：2026-06-09
**状态**：已确认

### 问题

新建项目设计 vs 已有系统改造，哪个是更重要的使用场景？

### 讨论

讨论中明确：已有污水处理系统的提标改造、工艺优化、环节调优是更高频的使用场景。例如对某些水处理单元中的流场、池子形状进行仿生改造。

### 决策

**提标改造场景通过专门的 `retrofit-router.json` 支持。**

改造场景路由以现有设备/工艺类型为主键（如曝气池、二沉池、MBR 膜组件），包含：
- 常见问题（如曝气池死区、二沉池短流）
- 关联领域
- 仿生改造策略
- 参考参数

原型模板中也专门设有"改造与优化启示"章节（第 4 章），面向已有系统的改造场景。

## DD-012：分支隔离的实施方式

**日期**：2026-06-09
**状态**：已执行

### 问题

如何实现新项目与旧项目的完全隔离？

### 决策

**使用 orphan branch（孤立分支）。**

### 实施步骤

1. `git checkout -f main` 切换到 main
2. `git checkout --orphan wastewater-treatment-universal` 创建孤立分支
3. 备份新项目文件到临时目录
4. 清除所有旧文件（旧吸附库的 prototypes、taxonomy、docs 等）
5. 恢复新项目文件
6. `git add .` + `git commit` 创建首次提交

### 结果

分支与旧项目无任何共享文件和 git 历史。GitHub 上完全独立。

## DD-013：首个聚焦的消费者与单一契约（先验证后扩展）

**日期**：2026-06-10
**状态**：已确认

### 问题

库隐含约 4 个消费者（材料/微生物设计、反应器/系统设计、提标改造、运行调控），各自输入输出不同，不存在单一统一契约。先固化哪一个？

### 决策

**先固化"反应器/系统设计"这一个消费者契约**，其余消费者后续再扩。

契约实例：`输入 = 工艺 + 设计问题 + 约束 → 输出 = 反应器/系统尺度仿生设计建议 + 可进工具验证的参数 + 工程约束 + 溯源`。

### 理由

反应器/系统是新库相对旧库的真正增量、风险最高、最值得先证明。不追求万能契约——参考库架构由"如何被查询"反向决定，先把一个查询模式坐实。

**日期**：2026-06-10

## DD-016：配置空间为反应器/系统场景的组织主线

**日期**：2026-06-10
**状态**：已确认

### 决策

以 **BNR 配置空间导航**为反应器/系统场景的组织主线：三轴 = 实现方式（空间/时间/结构）× 序列拓扑 × 回流路由；四条不变量界定可行域（①除磷需先有真厌氧接触 ②硝化需稳定好氧+长SRT ③反硝化需缺氧+硝酸盐+碳 ④硝酸盐不得进厌氧）。命名工艺（AO/A²O/AAOA/Bardenpho/UCT/MUCT）是可行域内的点；自适应=运行时在空间内移动。

引入连续控制变量 `front_sharpness`（过渡带厚度 / bulk DO 设定），将"分立分区重配（空间）"与"SND 微区共存（结构）"统一为一条连续轴。大气锋面（移动反应锋面框架）仅作动力学描述与可解释性表述，**不计入原型池**。

### 理由

配置空间能充当去重器（如判出 Bardenpho 应并入 A²/O 切片而非单列），并以最少切片覆盖最大证据面。

## DD-017：可操作性/可改造性轴与领域权重原则

**日期**：2026-06-10
**状态**：已确认

### 决策

引入与"可计算性"正交的**可操作性/可改造性轴**。可操作杠杆按改造成本分级：近零改造（曝气/回流/加药/混合）< 小改造（导流板/填料/曝气头）< 大改造（池型/拓扑/菌群更替）。

**"三传一反"（`fluid-mechanics` 动量传递 + `mass-transfer` 质量传递 + `biochemical-reactions` 反应）横切所有工艺、占据可操作杠杆绝大部分，应赋予高权重。** 库的领域 `relevance` 与路由 `weight` 应显式编码可操作性；`retrofit-router` 与 `operation-router` 优先指向高可操作杠杆；原型模板"改造与优化启示"标注所依赖杠杆的改造层级。

### 推论：切片取舍判据

高可操作杠杆人人在调，仿生在此层证明非显然更难；低可操作结构改造易出新意却难落地。**甜点区 = 用廉价杠杆实现非显然效果**（A²/O 切片用"开关曝气"实现"移动锋面"正踩在此）。

## DD-018：库的角色边界 + 运行调控暂缓 + 微调为条件性消费者侧能力

**日期**：2026-06-10
**状态**：已确认

### 决策

1. **库不充当优化器或仿真引擎**（重申 DD-006）。库的职责是：(a) 用仿生候选**扩充消费者的决策变量/设计空间**（如"移动锋面"引入"缺氧重配"变量）；(b) 给参数边界并标注由哪个工具验证。全厂模型/多目标优化器/智能体是**消费者**。
2. **`operation-router` 暂缓**，待 A²/O 切片验证仿生在运行层是否有着力点。
3. 弱可计算领域（尤以抗冲击为宜）的**数据微调/ML 代理是条件性、消费者侧能力**，非库内容；其输出为待核实的参数估计，进库前仍走 verified/unverified 关；宜用物理信息/混合模型而非纯黑箱（保可解释性）。

### 理由

保证库不膨胀为仿真平台，同时让库产出能直接进入科学决策与全生物段多目标优化（落点在"系统/群落"领域的全厂模型）。
